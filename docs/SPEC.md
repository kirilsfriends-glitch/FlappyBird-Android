# Спецификация формата TRIGLYPH/1

Версия 1 · сентябрь 2026 · статус: стабильная

Документ описывает контейнер полностью — по нему можно написать совместимую
реализацию на любом языке. Все целые числа — **big-endian** без знака.
Конкатенация обозначается `‖`.

---

## 1. Общая структура

```
контейнер := ЗАГОЛОВОК ‖ ФРАГМЕНТ* ‖ ВНЕШНИЙ_MAC
ФРАГМЕНТ  := u32 длина ‖ байты
ВНЕШНИЙ_MAC := 64 байта (HMAC-SHA3-512)
```

В стелс-режиме поверх накладывается оболочка (раздел 8).

## 2. Заголовок

| Поле | Тип | Описание |
|---|---|---|
| `magic` | 8 байт | `54 52 47 4C 59 50 48 01` (`TRGLYPH\x01`) |
| `version` | u8 | `1` |
| `suite` | u8 | `1` = triple, `2` = dual, `3` = solo |
| `mode` | u8 | `1` = пароль, `2` = X25519 анонимный, `3` = X25519 с отправителем, `4` = сырой ключ |
| `kdf_id` | u8 | `1` = scrypt+PBKDF2, `2` = Argon2id+PBKDF2, `3` = HKDF (без пароля) |
| `profile_id` | u8 | `0` = fast, `1` = balanced, `2` = hard, `3` = paranoid |
| `pad_policy` | u8 | `0` = нет, `1` = Padmé, `2` = корзины, `3` = фиксированный блок |
| `flags` | u16 | битовое поле, см. ниже |
| `chunk_size` | u32 | размер фрагмента открытого текста, 1 … 2²⁴ |
| `salt` | u32 len ‖ байты | 32 случайных байта |
| `eph_pub` | u32 len ‖ байты | эфемерный публичный ключ X25519 (только режимы 2, 3) |
| `sender_pub` | u32 len ‖ байты | публичный ключ отправителя (только режим 3) |
| `recipient_hint` | u32 len ‖ байты | 8 байт `SHA3-256("TRIGLYPH/v1|recipient|" ‖ pk)`, пусто по умолчанию |
| `aad` | u32 len ‖ байты | открытые связанные данные |
| `commitment` | 32 байта | обязательство к ключу (раздел 5) |

Флаги:

| Бит | Имя | Значение |
|---|---|---|
| 0 | `PADDED_WHOLE` | набивка применена ко всему сообщению целиком |
| 1 | `PADDED_LAST` | набивка применена только к последнему фрагменту |
| 2 | `HAS_AAD` | присутствуют связанные данные |
| 3 | `STREAM` | контейнер создан потоковым кодировщиком |

**`header_prefix`** — заголовок без поля `commitment`. Он служит контекстом
вывода ключей, поэтому подмена любого параметра (сюиты, профиля, соли, AAD)
приводит к другому ключевому расписанию и отвергается на проверке обязательства.

## 3. Вывод мастер-секрета

### 3.1 Режим пароля (`mode = 1`)

```
pw      := UTF-8( NFKC( пароль ) )
если задан «перец»:  pw := SHA3-512("TRIGLYPH/v1|pepper|" ‖ перец ‖ "|" ‖ pw)
stage0  := SHA3-512("TRIGLYPH/v1|pw|" ‖ u32(len pw) ‖ pw)
stage1  := scrypt(stage0, соль = SHA3-256("TRIGLYPH/v1|salt|" ‖ salt), N, r, p, dkLen = 64)
stage2  := PBKDF2-HMAC-SHA512(stage1, salt ‖ "|pbkdf2", iters, dkLen = 64)
master  := SHA3-512("TRIGLYPH/v1|master|" ‖ stage1 ‖ stage2 ‖ salt ‖ u32(iters))
```

Параметры профилей:

| Профиль | N | r | p | Память | Итерации PBKDF2 |
|---|---|---|---|---|---|
| fast | 2¹³ | 8 | 1 | 8 МиБ | 20 000 |
| balanced | 2¹⁶ | 8 | 1 | 64 МиБ | 210 000 |
| hard | 2¹⁸ | 8 | 1 | 256 МиБ | 600 000 |
| paranoid | 2²⁰ | 8 | 2 | 1 ГиБ | 1 200 000 |

При `kdf_id = 2` ступень scrypt заменяется на
`Argon2id(t, m, p, соль = SHA3-256(…)[0:16], dkLen = 64)`.

### 3.2 Сырой ключ (`mode = 4`)

```
master := HKDF-SHA512(ikm = ключ, salt = salt, info = "TRIGLYPH/v1|rawkey", L = 64)
```

### 3.3 X25519 (`mode = 2, 3`)

```
esk        := случайные 32 байта,  epk := X25519(esk, 9)
ikm        := X25519(esk, pk_получателя) ‖ epk ‖ pk_получателя
если mode = 3:
    ikm   := ikm ‖ X25519(sk_отправителя, pk_получателя) ‖ pk_отправителя
master     := HKDF-SHA512(ikm, salt, "TRIGLYPH/v1|x25519", 64)
```

Общий секрет, равный нулю (точка малого порядка), отвергается.

## 4. Ключевое расписание

```
prk := HKDF-Extract(salt = "TRIGLYPH/v1|schedule|" ‖ header_prefix, ikm = master)
K_x := HKDF-Expand(prk, "TRIGLYPH/v1|" ‖ метка, длина)
```

| Ключ | Метка | Длина |
|---|---|---|
| `K1` | `layer1/xchacha20-poly1305` | 32 |
| `K2` | `layer2/aes-256-gcm` | 32 |
| `K3` | `layer3/threefish-1024-ctr` | 128 |
| `Kmac` | `outer/hmac-sha3-512` | 64 |
| `Knonce` | `nonce-derivation` | 32 |
| `Kcommit` | `key-commitment` | 32 |

Нонсы:

```
nonce(purpose, i, L) := HKDF-Expand(
        HKDF-Extract("TRIGLYPH/v1|nonce|", Knonce),
        purpose ‖ "|" ‖ u64(i), L)
```

`purpose` = `"L1"` (24 байта), `"L2"` (12 байт), `"L3"` (16 байт).

## 5. Обязательство к ключу

```
commitment := SHA3-256("TRIGLYPH/v1|commit|" ‖ Kcommit)
```

Расшифрование обязано сверить это поле **до** обработки данных и прекратить
работу при расхождении. Свойство: для контейнера невозможно подобрать второй
ключ, под которым он корректно расшифруется (защита от partitioning oracle).

## 6. Набивка

```
padded := u64(len(данные)) ‖ данные ‖ 0x00 …
```

Целевая длина:

* **Padmé** — `E = ⌊log₂ L⌋`, `S = ⌊log₂ E⌋ + 1`, `z = E − S`, округление вверх
  до кратного `2^z`. Рост ≤ 12 %, утечка O(log log L) бит.
* **Корзины** — 256, затем удвоение: 512, 1024, 2048 … Скрывает язык
  сообщения полностью в пределах корзины.
* **Фиксированная** — кратно заданному блоку.

`PADDED_WHOLE` применяется до нарезки на фрагменты, `PADDED_LAST` — только к
последнему фрагменту.

## 7. Обработка фрагмента

```
hdr_hash := SHA3-256(заголовок целиком, включая commitment)
aad_i    := hdr_hash ‖ u64(i) ‖ u8(последний ? 1 : 0)

c1 := XChaCha20-Poly1305(K1, nonce("L1", i, 24), открытый_текст, aad_i)
c2 := AES-256-GCM      (K2, nonce("L2", i, 12), c1,             aad_i)    # сюиты triple, dual
c3 := Threefish-1024-CTR(K3, nonce("L3", i, 16), c2)                      # сюита triple
```

Режим CTR для Threefish: блок счётчика `nonce ‖ u128(counter) ‖ 96 нулевых байт`,
твик = `nonce`.

Расшифрование выполняет шаги в обратном порядке; ошибка любого тега —
немедленный отказ без выдачи открытого текста.

## 8. Внешний MAC

```
M := HMAC-SHA3-512(Kmac, "TRIGLYPH/v1|outer|"
        ‖ u32(len заголовка) ‖ заголовок
        ‖ Σᵢ ( u64(i) ‖ u8(последний) ‖ u32(len cᵢ) ‖ cᵢ )
        ‖ "|end|" ‖ u64(число фрагментов) )
```

Сравнение — за константное время. Покрывает заголовок, порядок фрагментов и их
количество: перестановка, повтор, вставка и обрезание обнаруживаются.

## 9. Стелс-оболочка

```
prefix := 32 случайных байта
маска  := SHAKE-256("TRIGLYPH/v1|stealth|" ‖ prefix ‖ u64(номер блока)) , блок 64 КиБ
вывод  := prefix ‖ (контейнер ⊕ маска)
```

Маска выводится из **открытого** префикса и криптостойкости не добавляет —
это защита от поиска по сигнатуре, не более. Декодер распознаёт оболочку,
сняв маску с первых 8 байт и сравнив их с `magic`.

## 10. Броня

| Вид | Алфавит | Бит на знак | Обрамление |
|---|---|---|---|
| `hanzi` | U+4E00 … U+5DFF (4096 иероглифов) | 12 | префикс `㊀`/`㊁`/`㊂` = `len mod 3`, контрольная сумма 3 байта |
| `cyrillic` | `абвгдежзийклмнопрстуфхцчшщъыьэюя` (32) | 5 | контрольная сумма 2 байта |
| `latin` | Base64URL без набивки | 6 | — |
| `grouped` | Base32, группы по 5 через дефис | 5 | контрольная сумма 2 байта |

Контрольная сумма: `SHA3-256("TRIGLYPH/armor|" ‖ данные)`, первые N байт.

При автоопределении декодер обязан пробовать брони с контрольной суммой
(`hanzi`, `cyrillic`, `grouped`) раньше `latin`: алфавит Base64URL включает в
себя Base32, поэтому иначе короткая строка была бы разобрана неверно без
всякой ошибки.

Текстовая обёртка (необязательная):

```
-----TRIGLYPH BEGIN / НАЧАЛО / 开始-----
Suite: triple
Armor: hanzi

㊁卅假勅坐劀企丐企一倀丐丁…
-----TRIGLYPH END / КОНЕЦ / 结束-----
```

## 11. Формат частей секрета (схема Шамира)

```
часть := 0xA5 ‖ u8 индекс ‖ u8 порог ‖ u8 всего ‖ y-байты ‖ 4 байта контрольной суммы
```

Секрет перед разрезанием дополняется четырьмя байтами
`SHA3-256("TRIGLYPH/secret|" ‖ секрет)`, поэтому неверный набор частей
обнаруживается при сборке. Поле GF(2⁸) задаётся полиномом `0x11B`.

## 12. Требования к совместимой реализации

1. Проверять `magic` и `version`; неизвестную версию — отвергать.
2. Сверять обязательство к ключу до любых других действий над данными.
3. Проверять внешний MAC за константное время.
4. Никогда не выдавать открытый текст до успешной проверки всех тегов
   соответствующего фрагмента.
5. Ограничивать `chunk_size` (реализация на Python допускает не более 2²⁴)
   и длину заголовка, чтобы чужой файл не смог исчерпать память.
6. Генерировать `salt` и `esk` только криптостойким генератором.
